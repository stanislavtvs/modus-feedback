# Концепция и техническое решение

## Проблема и ценность

Обращения сотрудников поступают через встречи, почту и разговоры, теряют владельца и не возвращаются автору с результатом. Продукт собирает их в одном реестре, назначает ответственного и сохраняет обсуждение и решение. Сотрудник получает прозрачность, руководитель — очередь работы, компания — историю улучшений.

Видео организатора (локальная автоматическая расшифровка): примерно 01:03–01:54 описывает хаотичные каналы и потерю доверия при отсутствии результата; 01:54–02:34 — единый модуль, видимый статус, уточнения и отчётность. Распознавание может содержать ошибки; точные цитаты из него не используются. Эти темы согласуются с письменным ТЗ.

## Пользователи и сценарии

Сотрудник создаёт проблему, предложение либо положительный отзыв, прикладывает материал, видит ответственного, срок и обсуждение. Руководитель уточняет ситуацию, задаёт приоритет, при необходимости переназначает, фиксирует решение. Администратор настраивает категории, сроки и маршруты, разбирает обращения без ответственного. Собственник может получить административную обзорную роль; для промышленного внедрения нужна отдельная роль наблюдателя без права изменения.

Основной сценарий: автор → категория → автоматическое назначение → рассмотрение → уточнение с комментарием автора → работа → мотивированный итог. Ни один итоговый статус не сохраняется с пустым результатом. Завершённое обращение можно открыть снова, сохранив предыдущий результат в истории.

## Архитектура

Браузер → Django templates / сессии / CSRF → прикладные представления и сервисы → PostgreSQL. Gunicorn обслуживает приложение, WhiteNoise — статические ресурсы. Файлы лежат в отдельном приватном Docker volume и скачиваются через проверяющий права обработчик. Два сервиса Compose, приложение запускается непривилегированным пользователем.

Django выбран ради единого стека форм, авторизации, ORM, миграций и административного интерфейса. PostgreSQL — для транзакций, индексов и дальнейшего полнотекстового поиска. Серверные шаблоны сокращают сложность клиента и сохраняют основные сценарии без JavaScript. JavaScript используется для пользовательских настроек доступности и помощника Gemma; основной процесс работает без него.

Модель: User + Profile(role, department), Department, Category(responsible, sla_days), Ticket, Comment, Event, Attachment, Notification. Ticket хранит автора, подразделение на момент создания, назначение, статус, сроки, первый ответ и результат. Event сохраняет актёра, время и изменённые значения. Профиль и категории управляются администраторами. Операции обработки используют транзакцию и блокировку строки PostgreSQL.

## Безопасность

Разграничение на сервере применяется к спискам, карточкам, аналитике, похожим обращениям и файлам. CSRF для всех изменений, выход через POST, экранирование текста шаблонами, пароли Django, параметры из окружения, DEBUG выключен. Административная карточка обращения доступна только для чтения, чтобы изменения проходили через процесс с историей. Прямой доступ к базе и инфраструктуре контролируется отдельно.

Уведомления создаются в той же транзакции, что изменение. Сроки и очередь без назначения видны в реестре администратора; фоновая отправка напоминаний пока не реализована. SLA считается в календарных днях, без производственного календаря.

## Метрики и проверка полезности

Доля завершённых = (реализовано + отклонено + закрыто) / все доступные обращения. Отдельно считаются реализованные улучшения и наличие текста решения/уточнения. Время первого ответа — среднее от регистрации до первой реплики или изменения от руководителя/администратора, отличного от автора; применяется только к записям с ответом. Это рабочее приближение, а не измерение трудозатрат. Тестовые даты и результаты демонстрационных записей не являются фактическими показателями компании.

Пилот на одном подразделении на 2–4 недели: сравнить число потерянных обращений, время ответа и долю мотивированных итогов с исходным процессом; попросить сотрудников выполнить подачу и найти результат без подсказок. Отдельно пригласить пользователей клавиатуры и скринридера. Целевые значения согласовать с владельцем процесса до пилота.

## Развитие

MVP: внутренняя подача, маршрутизация, обсуждение, решение, роли, аналитика, доступный интерфейс. Далее: SSO, роль наблюдателя, email и фоновые напоминания, рабочий календарь, антивирус, расширение вложений, уведомления об изменении маршрутов, автоматические accessibility-проверки CI. Отдельная проработка: семантические кластеры, клиентская обратная связь, NPS, интеграции с корпоративными системами.

Битрикс24: исходящее создание задачи после назначения, входящий статус по webhook, идентификатор обращения и сотрудника, категория и согласованный минимум текста. 1С: при необходимости чтение справочника подразделений/сотрудников; содержание обращений без согласования не передавать. До реализации уточнить API и версии, источник истины, идентификаторы, права, лимиты, расположение данных, обработку повторов, конфликты статусов и юридические основания. Реальных интеграций и их имитаций в этом MVP нет.

## Помощник Gemma

Добавлен серверный вызов Ollama в частной VPN-сети для формулировки и разбора обращений. Это вспомогательный инструмент, не автоматический диспетчер или механизм оценки сотрудников. Структура ответа проверяется, роль пользователя ограничивает доступный контекст. Вложения и данные профилей не включаются. Полный перечень настроек, данных и ограничений — в README.
